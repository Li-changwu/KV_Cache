\title{面向超长上下文推理的 KV Anti-Caching}
\author{}
\date{}

\begin{document}

\begin{frame}[t]{What is your problem}
\small
\vspace{-0.5em}

\textbf{\textcolor{MainBlue}{背景：Agent 与科学发现推理正在把上下文长度推到 1M tokens}}

\vspace{0.2em}
生产级长上下文推理中，历史对话会在 prefill 阶段生成的 KV 状态，需要在后续多轮请求的 prefill 与 decode 中持续、准确地复用。随着上下文长度扩展到 128K 乃至 1M tokens，KV 已不再是单次请求的临时缓存，而是随会话、文档和工具轨迹持续增长的服务状态。

\vspace{0.8em}

\begin{beamercolorbox}[wd=\linewidth,sep=0.7em,rounded=true]{block body}
\textbf{\textcolor{AccentRed}{核心问题：}}
% 当可复用 KV 状态的规模超过 GPU 显存容量时，现有前缀缓存和 KV 卸载机制难以有效支撑此类工作负载：推理引擎内的热缓存通常不具备跨会话持久性，而基于 SSD 的按需取回机制可能在 prefill 或 decode 的关键路径上引入阻塞。

现有工作通过引擎内前缀缓存、外部 KV 存储以及基于 SSD 的数据搬移来改善 KV 复用，但它们仍然对一个关键的状态管理问题探索不足：当可复用的历史 KV 超出 GPU 显存时，冷 KV 对象虽然持久化保存，却并未处于可执行状态；若在预填充或解码阶段才去发现它，就可能将存储 I/O 转化为在线的尾部延迟。
\end{beamercolorbox}

\end{frame}

\begin{frame}[t]{Why it matters? }
\vspace{0.35em}

\begin{block}{1、长上下文多轮对话正在成为 LLM 服务的重要形态}
企业级 RAG、代码助手和多智能体工作流通常围绕文档、代码库、任务状态和历史交互持续展开，而不是一次性问答。因此，系统性能瓶颈不再只来自单次请求计算，也越来越来自如何高效承载和复用长历史上下文。
\end{block}

\vspace{0.35em}

\begin{block}{2、KV 多级存储正在成为支撑长上下文服务的必要机制}
长上下文 KV 状态会随 token 数、模型层数和并发请求数快速增长，GPU 显存难以长期容纳所有可复用 KV。因此，将 KV 扩展到 CPU 内存和 SSD 等更大容量层级，是突破显存限制、降低重复 prefill 成本的重要方向。
\end{block}

\vspace{0.35em}

\begin{block}{3、KV 跨请求复用决定了多轮长上下文服务能否真正高效}
对于多轮 RAG、代码助手和 Agent 任务，后续请求往往会反复引用前序历史上下文。如果历史 KV 不能跨请求持久保存和准确复用，系统就只能反复重算相同上下文，导致 TTFT、吞吐和服务成本显著恶化。
\end{block}
\end{frame}

\begin{frame}[t]{Why existing work fail? 为什么已有工作没有解决？}
\fontsize{6.8pt}{7.6pt}\selectfont
\vspace{-0.8em}

\setlength{\tabcolsep}{2.4pt}
\renewcommand{\arraystretch}{1.25}
\begin{tabularx}{\linewidth}{

>{\centering\arraybackslash}p{0.20\linewidth}
>{\raggedright\arraybackslash}p{0.29\linewidth}
>{\raggedright\arraybackslash}X}
\rowcolor{gray!35}
\textbf{类别} & \textbf{代表方法} & \textbf{具体措施} & \textbf{关键不足} \\
\hline

GPU 内 KV 管理 &
PagedAttention, APC, RadixAttention &
将 KV 切块管理，并用哈希表或前缀树复用相同前缀，减少显存碎片和重复预填充。 &
主要解决 \textbf{HBM/CPU 内热 KV 的管理与复用}；一旦历史 KV 超出容量并进入 SSD/外部冷层，就缺少持久化对象抽象、精确定位协议和恢复前 SLA 预算。 \\
\hline

PD 分离与跨实例 KV 传输 &
DistServe, Splitwise, NIXL connector, Mooncake &
分离预填充和解码实例，并在阶段之间传递 KV，降低资源干扰。 &
解决阶段隔离，但没有把长期历史 KV 当作可恢复的服务状态来管理。 \\
\hline

外部 KV 缓存层 &
LMCache, Mooncake &
在推理引擎外维护 KV 缓存，支持跨请求、跨实例复用，并扩展到主存或 SSD。 &
偏缓存扩容；缺少超长历史 KV 的精确索引、恢复屏障和执行前就绪保证。 \\
\hline

冷层存储与恢复调度 &
Tutti, CacheFlow, DualPath, FlexGen, Infinite-LLM &
从主存、SSD 或远端存储恢复 KV，并用流水、并行和调度隐藏 I/O。 &
主要回答 \textbf{如何把 KV 搬得更快}；没有系统回答多轮历史 KV 何时变冷、何时恢复、恢复不完能否准入，冷 I/O 仍可能暴露在 TTFT 临界路径。 \\
\hline

文档片段复用 &
CacheBlend, RAGCache &
面向 RAG 或多文档场景复用共享文档、chunk 或非严格前缀 KV，通过融合或选择性重算降低 TTFT。 &
主要复用文档片段，不等价于完整会话历史；难以直接支撑精确长上下文复用。 \\
\hline

近似、压缩与驱逐 &
H2O, Scissorhands, CacheGen, TTKV, KVDrive &
通过压缩、量化或重要性筛选降低 KV 容量和带宽开销。&
可以缓解容量/带宽瓶颈，但可能改变精确 attention 语义；不适合作为 1M 级精确长上下文服务的基础机制。 \\

\end{tabularx}

\vspace{0.35em}
\begin{beamercolorbox}[wd=\linewidth,sep=0.5em,rounded=true]{block body}
\textbf{\textcolor{AccentRed}{总结：}}
已有工作分别优化了 `KV 如何复用''、`KV 如何传输'' 和 ``KV 如何搬得更快''；
但它们普遍没有把长期历史 KV 抽象为 \textbf{可持久化、可索引、可恢复、可准入的 serving state}，
因此无法在 1M 级多轮长上下文服务中稳定避免重复 prefill 与 decode-path cold I/O。
\end{beamercolorbox}

\end{frame}

\begin{frame}[t]{What is your key idea?}
\small
\vspace{-0.45em}

\begin{beamercolorbox}[wd=\linewidth,sep=0.55em,rounded=true]{block body}
\textbf{\textcolor{MainBlue}{核心思想：}}
将多轮长上下文服务中的历史 KV 从“临时缓存”提升为“可持久化、可索引、可恢复到可执行状态、可准入控制的服务状态”，并通过 KV Evicted Index 与 KV PrePass 在请求进入 LLM 引擎前完成冷 KV 发现、校验与恢复，从而避免 SSD 冷数据访问阻塞 prefill 或 decode 关键路径。
\end{beamercolorbox}

\vspace{0.35em}

\begin{block}{Challenge 1：如何在多级存储中持续追踪历史 KV 的状态？}
长上下文 KV 可能在 GPU HBM、CPU DRAM、SSD 或 3FS 之间迁移，离开 GPU 后就不再是引擎内部直接可见的 hot cache。系统必须持续记录每段 KV 的 token 范围、层范围、correctness key、存储位置和 ready 状态，否则无法判断它是否仍然存在、是否可用以及能否被恢复。
\end{block}

\vspace{0.35em}

\begin{block}{Challenge 2：如何在请求进入 LLM 引擎之前判断其所需 KV 的冷热状态？}
一个多轮请求可能依赖大量历史 KV 范围，其中一部分已经在 GPU/CPU 中 ready，一部分可能只在 SSD/3FS 中 cold，还有一部分可能正在恢复、缺失或与当前请求不匹配。系统必须在执行前枚举这些所需历史 KV，并将它们分类为 GPU-ready、CPU-ready、SSD-cold、fetching、loading、missing 或 mismatch，从而生成明确的 reuse plan 和 restore plan。
\end{block}

\vspace{0.35em}

\begin{block}{Challenge 3：如何避免冷 KV 恢复阻塞在线执行路径？}
即使系统知道某段历史 KV 在 SSD 上，也不能让请求进入 prefill 或 decode 后再同步等待 SSD 读取，否则冷数据访问会直接放大 TTFT、TPOT 和尾延迟。系统必须在请求进入 LLM 引擎之前，基于所需 KV 的状态做出准入决策：如果存在 cold KV，则提前发起异步恢复，并在恢复完成前拒绝或延迟请求；如果恢复不完又不能准入，则必须有 fallback 策略（如部分预填充、部分重算、降级或拒绝），以避免冷 I/O 失控。
\end{block}

\end{frame}

\begin{frame}[t]{What is your key idea? 需要解决哪些挑战？}
\small
\vspace{-0.35em}

\begin{block}{Challenge 3：如何组织 cold object，避免恢复读放大？}
如果一个 1M session 的冷对象很大，而本轮只需要其中一小段，整对象恢复会浪费带宽并污染 DRAM。
如果对象太碎，又会带来海量小文件、随机 I/O 和元数据开销。

\vspace{0.25em}
\textbf{\textcolor{AccentRed}{挑战本质：}}
在 KV range 粒度和 3FS/NVMe 友好对象粒度之间建立可 partial promote 的布局。
\end{block}

\vspace{0.35em}

\begin{block}{Challenge 4：如何在多资源约束下准入请求？}
restore 不是单一磁盘读，还会消耗 3FS/SSD、network/RDMA、DRAM、H2D、GPU slack，
并可能影响短请求 P99。低局部性长请求如果盲目进入队列，会拖垮整个服务。

\vspace{0.25em}
\textbf{\textcolor{AccentRed}{挑战本质：}}
把 TTFT、hit rate、带宽水位、deadline miss 和短请求隔离统一进 admission decision。
\end{block}

\end{frame}

\begin{frame}[t]{What is your key idea? 三个挑战对应三个设计}
\fontsize{6.8pt}{7.4pt}\selectfont
\vspace{-0.8em}

\begin{columns}[T,onlytextwidth]
\begin{column}{0.49\textwidth}
\begin{block}{Challenge 1：Prefill/Decode 前不知道 required KV}
冷层 miss 若在 prefill reuse 或 decode execution 才被发现，SLA 已不可控。
\end{block}
\end{column}
\begin{column}{0.49\textwidth}
\begin{block}{Design 1：KVPrePass + Residency Table}
请求进入 vLLM 前，基于 correctness key 和 session lineage 枚举
\texttt{ready\_set / cold\_set / missing\_set}。

\vspace{0.1em}
\textbf{\textcolor{AccentRed}{输出：}}本轮 required KV ranges。
\end{block}
\end{column}
\end{columns}

\vspace{0.05em}

\begin{columns}[T,onlytextwidth]
\begin{column}{0.49\textwidth}
\begin{block}{Challenge 2：冷对象恢复容易读放大}
整块恢复浪费带宽；过细切分又导致元数据和 I/O 抖动。
\end{block}
\end{column}
\begin{column}{0.49\textwidth}
\begin{block}{Design 2：Cold Object + Partial Promote}
把细粒度 KV ranges 打包成 3FS/NVMe 友好 cold object，
只把本轮需要的 ranges promote 到 DRAM ready。

\vspace{0.1em}
\textbf{\textcolor{AccentRed}{输出：}}useful bytes 可观测的恢复计划。
\end{block}
\end{column}
\end{columns}

\vspace{0.05em}

\begin{columns}[T,onlytextwidth]
\begin{column}{0.49\textwidth}
\begin{block}{Challenge 3：恢复与重算会竞争多种资源}
3FS、network、H2D、DRAM 和 GPU slack 都可能成为尾延迟来源。
\end{block}
\end{column}
\begin{column}{0.49\textwidth}
\begin{block}{Design 3：Budgeted Scheduler + Two-Phase Barrier}
用多资源预算和 deadline 控制 restore / recompute fallback；
只有 required ranges 对 prefill reuse 与 decode 都 ready，admission 才能返回 ADMIT。

\vspace{0.02em}
\textbf{\textcolor{AccentRed}{输出：}}无重算失控、无同步 cold miss 的准入决策。
\end{block}
\end{column}
\end{columns}

\vspace{0.1em}
\begin{beamercolorbox}[wd=\linewidth,sep=0.35em,rounded=true]{block body}
\textbf{\textcolor{AccentRed}{一句话贡献：}}
通过\textbf{KVPrePass + partial promotion + budgeted non-blocking restore}，
把 1M 历史 KV 从 ``机会式缓存命中或失败重算'' 变成 ``SLA 受控的服务协议''。
\end{beamercolorbox}

\end{frame}

\begin{frame}[t]{Request Lifecycle: Anti-Caching 如何处理一个请求？}
\footnotesize
\vspace{-0.45em}

\begin{block}{1. Commit：把成功请求的历史 KV 变成可复用状态}
connector 保存 layer KV；control plane 记录 correctness key、token range、layout、checksum 和版本；
后台策略决定哪些 ranges 后续可以 demote 到 cold tier。
\end{block}

\vspace{0.25em}

\begin{block}{2. Demotion：把冷 KV 从执行层移动到容量层}
当 HBM/DRAM 水位升高，系统选择低复用价值 ranges，打包成 cold object 写入 local NVMe 或 3FS。
只有 checksum / manifest commit 成功后，才释放执行层副本并标记 \texttt{ready=false}。
\end{block}

\vspace{0.25em}

\begin{block}{3. KVPrePass + Restore/Fallback：请求到来时先枚举 required KV}
若全部 required ranges 已在 HBM/DRAM ready，则 ADMIT；
若存在 cold ranges，则生成后台 restore task；
若 correctness mismatch 或 missing，则 partial prefill / full fallback / delay / reject。
\end{block}

\vspace{0.25em}

\begin{block}{4. Two-Phase Ready Barrier：恢复完成后才允许复用和生成}
restore 将 selected ranges 标记为 DRAM ready；
barrier 验证 prefill reuse 所需历史 KV ready、decode 所需 KV ready，且 \texttt{sync\_3fs\_miss\_total=0}；
通过后再进入 vLLM prefill/decode。
\end{block}

\end{frame}

\begin{frame}[t]{What is the takeaway}
\small
\vspace{1.0em}

\begin{beamercolorbox}[wd=\linewidth,sep=1.05em,rounded=true]{block body}
\Large
\centering
\textbf{
我们的真正问题不是 ``如何设计一个 KV Anti-Caching 调度器''，
而是现有推理服务无法让百万级历史 KV 在精确语义下同时满足容量、
Prefill 复用 ready、Decode 执行 ready 和 TTFT SLA。
}
\end{beamercolorbox}

\vspace{0.7em}

\begin{beamercolorbox}[wd=\linewidth,sep=0.95em,rounded=true]{block body}
\large
\centering
\textbf{
KV Anti-Caching 的核心价值，是把冷层 KV miss 从 Prefill 重算和 Decode 同步等待中移出，
通过 pre-pass、partial promotion 和 budgeted restore/fallback，
让长上下文复用成为可控制的服务协议。
}
\end{beamercolorbox}
